> 状态：待实施

> 当前基线版本：`2026.07.20.17`  
> 适用对象：后续维护者与 AI Agent

## 1. 文档目的

本文不是一次性需求说明，而是 Sksir New 重构的阶段化施工手册。后续 Agent 应当按本文顺序逐阶段实施、验证和交付，不得把全部重构合并为一次大改。

每个阶段都包含：

- 明确目标与非目标；
- 前置条件和输入；
- 推荐涉及的文件；
- 可执行的详细步骤；
- 必须保持的兼容边界；
- 自动检查与人工验收；
- 阶段交付物；
- 进入下一阶段的条件。

本文描述的是目标方案。实际实施前仍要读取当时的代码和 `git status`，不能假设代码与本文制定时完全一致。

## 2. 已确认的产品决定

以下决定已经由项目维护者确认，后续 Agent 不应反复询问，除非维护者主动改变方向。

### 2.1 “添加标签”的含义

维护者所说的“添加标签麻烦”，主要是指新增一个网站收藏条目麻烦，而不是要求一个网站必须支持复杂的多标签体系。

因此：

- 第一优先级是降低“新增网站”的操作成本；
- 可以保留分类筛选能力；
- 数据结构可以为以后支持多个语义标签留出空间；
- 第一阶段不得为了多标签系统引入复杂交互或复杂数据迁移。

### 2.2 视觉方向

新版继续采用“壁纸 + 极简玻璃感”，不改成厚重的后台面板或传统门户网站。

视觉关键词：

- 克制；
- 通透；
- 留白；
- 清晰层级；
- 低干扰；
- 轻量自然动画；
- 壁纸可见但文字始终可读；
- 桌面端精致，移动端不拥挤。

玻璃效果不得以牺牲首屏速度、文字可读性或低配设备流畅度为代价。`html.perf-lite` 和 `prefers-reduced-motion` 下必须有简化效果。

### 2.3 收藏维护方式

收藏只要求在本地电脑维护。

因此：

- 不建设线上管理后台；
- 不接数据库；
- 不接 GitHub API；
- 不做账号、登录、认证或多端同步；
- 推荐提供本地可视化收藏编辑器；
- 可以附带命令行工具作为批量维护或兜底方式；
- 线上站点不得暴露可写入仓库的管理接口。

## 3. 当前基线与主要问题

本文制定时的只读检查结果如下：

- 项目为纯静态页面，部署目标保持不变；
- `index.html` 约 40 KB，包含较多早期启动及 iOS 高度逻辑；
- `css/style.css` 约 76 KB，桌面、移动端、iOS、动画和组件样式集中维护；
- `js/main.js` 约 32 KB；
- `js/set.js` 约 72 KB；
- `data/sites.js` 约 33 KB；
- 收藏数据为 6 个分组、86 个站点；
- 收藏数据校验为 0 错误、0 警告；
- 主前端脚本中约有 249 处 jQuery 使用；
- 收藏已经做到打开面板后再加载；
- 状态检测已经做到用户需要时再加载；
- 首屏同步样式请求已经收敛为一个主样式；
- 当前工作区在制定计划时无未提交改动。

主要问题不是技术栈过重，而是：

1. 首页、收藏和设置的展示层级不够清楚；
2. 新增网站需要手写较多重复字段；
3. 新增分类需要同步维护分类数组；
4. 大型 CSS 和 JavaScript 文件职责交叉，修改成本逐渐升高；
5. 设置项过于集中，快捷入口与性能设置等概念混放；
6. 现有 jQuery 使用广泛，不能低风险地一次性移除；
7. iOS 兼容逻辑敏感，视觉重构容易误伤已经稳定的行为。

## 4. 总体目标与性能预算

### 4.1 产品目标

重构完成后应达到：

- 首屏突出时间、搜索、常用入口、收藏和设置；
- 收藏面板更容易浏览、搜索和筛选；
- 新增网站通过本地表单完成，不需要手写大段 JavaScript；
- 设置项重新分组，常用设置更容易理解；
- 数据、渲染、交互和样式的职责边界清楚；
- 日常维护命令简洁、可重复；
- 不破坏 PC、安卓和 iPhone Safari 的现有能力。

### 4.2 性能预算

实施过程中应持续守住以下预算：

- 首屏核心结构目标约 0.5 秒可见；
- 时间、搜索框、基础布局和壁纸优先；
- 收藏数据不得阻塞首屏；
- 状态检测不得在未打开收藏时加载；
- 首屏不得批量下载远程收藏图标；
- 首屏真实 stylesheet 链接仍位于早期启动脚本之后；
- 主样式可保持单请求，避免为了代码组织增加阻塞请求；
- 输入响应和高频布局更新继续使用 `requestAnimationFrame` 合帧；
- 动画仅使用适合合成的属性，尽量避免高频改变布局；
- 低性能模式禁用或简化模糊、阴影和复杂动画。

这些是目标预算，不允许 Agent 为追求跑分而破坏视觉稳定、离线容错或 iOS 体验。

## 5. Agent 执行协议

### 5.1 开始任何阶段前

Agent 必须：

1. 完整阅读根目录 `AGENTS.md`；
2. 完整阅读本文；
3. 运行 `git status --short`；
4. 阅读当前阶段涉及的全部相关文件；
5. 阅读前一阶段的交付记录；
6. 确认没有覆盖维护者已有修改；
7. 只处理当前阶段的范围。

若工作树已有修改：

- 保留用户修改；
- 判断是否与当前阶段重叠；
- 不得使用 `git reset --hard` 或类似方式清理；
- 无法安全绕开时向维护者说明冲突。

### 5.2 阶段实施规则

- 一次只实施一个阶段；
- 不允许边做数据迁移边顺手重画全部页面；
- 优先小范围原生 JavaScript 和 CSS；
- 不引入 React、Vue、Vite、大型 UI 框架或无必要依赖；
- 新代码优先原生 JavaScript，旧 jQuery 代码按模块渐进迁移；
- 不以“现代化”为由一次性删除 jQuery；
- 不恢复已删除的旧 CSS 或 JS 文件；
- 不重新启用 Service Worker 缓存或安装能力；
- 不猜测性修改 iOS 键盘和整页位移逻辑；
- `奖励` 分组继续视为前端隐藏内容，不得擅自公开；
- 正式功能改动必须更新版本；
- 纯文档变更不要求更新功能版本。

### 5.3 每个阶段完成后

至少运行：

```powershell
node scripts\check.js
git diff --check
```

正式功能改动还要运行：

```powershell
node scripts\update-version.js YYYY.MM.DD.N
```

版本号中的 `N` 必须基于当时项目版本和当天已有版本顺延，不得照抄本文示例。

阶段交付说明必须包含：

- 完成了什么；
- 修改了哪些文件；
- 有哪些刻意没有做；
- 自动检查结果；
- 人工测试结果；
- 已知问题；
- 下一阶段是否已具备条件。

### 5.4 阶段状态记录

执行阶段的 Agent 应在本文末尾“实施记录”中追加记录，但不要改写历史记录。建议格式：

```markdown
### Phase N - YYYY-MM-DD - 版本号

- 状态：完成 / 部分完成 / 阻塞
- 修改摘要：
- 自动检查：
- 人工检查：
- 已知问题：
- 下一步：
```

├── wallpaper.js              # 壁纸读取、预加载和切换

- 管理器的源数据可以是 JSON，线上运行格式可以由脚本生成；
- 不允许为了目录整齐一次性拆出大量同步请求；
- 拆分代码的价值是职责清晰，加载方式仍要服从首屏性能。

## 7. 目标数据模型

第一目标是让新增网站简单，不是建立复杂内容管理系统。

推荐的规范化站点记录：

```json
{
  "id": "github",
  "name": "GitHub",
  "url": "https://github.com/",
  "group": "常用",
  "category": "开发部署",
  "description": "代码托管与协作平台",
  "icon": "auto",
  "featured": true,
  "statusCheck": true
}
```

字段定义：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 是 | 稳定唯一标识；改名或改 URL 时尽量不变 |
| `name` | 是 | 网站显示名称 |
| `url` | 是 | 仅允许绝对 `http` 或 `https` URL |
| `group` | 是 | 一级分组，如常用、影音、工具 |
| `category` | 否 | 组内筛选分类；为空时归入默认分类 |
| `description` | 否 | 简短说明，移动端可按空间省略 |
| `icon` | 否 | `auto`、本地资源或远程资源 |
| `featured` | 否 | 是否允许作为首页快捷入口候选 |
| `statusCheck` | 否 | 是否允许状态检测 |
| `hidden` | 否 | 是否默认不公开展示 |

设计规则：

- `target="_blank"` 与 `rel="noopener noreferrer"` 由渲染器统一提供，不再逐条重复；
- 布尔值必须是真正的布尔类型；
- 分组、分类列表从条目自动推导；
- `id` 必须唯一且稳定；
- URL 必须校验协议；
- 图标为空或为 `auto` 时使用统一的自动与回退策略；
- 旧的 `skipCheck`、`favoriteCheck` 需要在迁移规则中明确映射；
- `奖励` 分组的隐藏和解锁逻辑必须完整保留；
- 不得因为规范化数据而意外公开隐藏内容。

如果后续确有多标签需求，可以新增 `tags: []`，但不属于第一轮必须功能。

## 8. Phase 0：建立基线与冻结决策

### 8.1 目标

在动代码前建立可比较、可回退的基线，明确新版页面的信息架构和验收尺寸。

### 8.2 非目标

- 不改视觉；
- 不改数据；
- 不迁移 JavaScript；
- 不更新功能版本。

### 8.3 执行步骤

1. 记录当前 `git status` 和版本号。
2. 运行现有统一检查并保存结果。
3. 统计首屏关键资源：
   - HTML；
   - 主 CSS；
   - 首屏 defer 脚本；
   - 字体；
   - 壁纸；
   - 首屏前是否请求收藏数据；
   - 首屏前是否请求状态检测。
4. 在以下视口记录当前截图：
   - 桌面：1440 × 900；
   - 小型桌面：1280 × 720；
   - 安卓参考：412 × 915；
   - iPhone 参考：390 × 844；
   - iPhone 小屏：375 × 667。
5. 记录以下流程：
   - 首次打开；
   - 搜索框聚焦；
   - 搜索建议出现；
   - 收藏打开；
   - 分类切换；
   - 设置打开；
   - 壁纸切换。
6. 为新版画三个低保真线框：
   - 首页；
   - 收藏中心；
   - 设置中心。
7. 在线框中确认：
   - 首页快捷入口数量；
   - 收藏按钮位置；
   - 设置按钮位置；
   - 桌面收藏面板尺寸；
   - 手机收藏使用全屏还是底部抽屉；
   - 卡片是否始终显示描述。
8. 把截图、测量结果和线框说明保存到 `docs/baseline/`。

### 8.4 推荐默认方案

如果维护者没有补充选择，使用：

- 桌面首页显示 8 个快捷入口；
- 手机显示 6 个；
- 桌面收藏为大尺寸居中玻璃面板；
- 手机收藏为接近全屏的面板；
- 桌面卡片显示描述；
- 小屏手机允许隐藏描述；
- 设置为独立玻璃面板，不与收藏混在同一视图。

### 8.5 验收标准

- 有完整基线数据和截图；
- 有三个页面的线框说明；
- 确认首屏收藏和状态检测仍为延迟加载；
- `node scripts\check.js` 通过；
- `git diff --check` 通过；
- 未发生功能代码修改。

### 8.6 交付物

- `docs/baseline/README.md`；
- 基线截图；
- 资源与加载时序记录；
- 三个页面线框；
- Phase 0 实施记录。

## 9. Phase 1：视觉基础与页面骨架

### 9.1 目标

在不改变核心功能的前提下，建立极简玻璃视觉系统和清楚的页面层级，为后续收藏与设置重构提供稳定骨架。

### 9.2 前置条件

- Phase 0 已完成；
- 已有基线截图；
- 已确认主要视口布局；
- iOS 敏感规则位置已经识别。

### 9.3 主要涉及文件

- `index.html`
- `css/style.css`
- 必要时少量修改 `js/main.js`

### 9.4 执行步骤

1. 在 `:root` 建立设计变量：
   - 玻璃背景；
   - 边框颜色；
   - 主文字与次文字；
   - 阴影；
   - 圆角；
   - 间距；
   - 动画时长；
   - 页面最大宽度。
2. 不改变线上单主样式策略，仅重新整理 `style.css` 内部分区。
3. 明确首屏层级：
   - 时间和日期；
   - 搜索；
   - 快捷入口；
   - 收藏与设置入口；
   - 页脚。
4. 统一玻璃面板语言：
   - 背景透明度；
   - 细边框；
   - 轻阴影；
   - 可控模糊；
   - hover 与 active 状态。
5. 保证壁纸较亮时文字仍可读，可使用局部遮罩或文字阴影，但不得叠加过重全屏黑层。
6. 高配设备保留完整模糊和过渡。
7. `html.perf-lite` 下减少：
   - `backdrop-filter`；
   - 大面积阴影；
   - 连续滤镜动画；
   - 非必要淡入。
8. `prefers-reduced-motion` 下关闭位移动画和装饰动画。
9. 保留 `.all-search` 的明确 `translateY(0)` 及 transform 过渡。
10. 保留搜索态隐藏 placeholder。
11. 移动与 iOS 覆盖继续放在 `style.css` 末尾，并使用既有媒体查询和 HTML 类限定。
12. 不改变壁纸 `object-fit`、fixed 定位、安全区扩展和 iOS 背景变量含义。

### 9.5 禁止事项

- 不重写 iOS 键盘策略；
- 不根据 `visualViewport.offsetTop` 移动整个页面；
- 不加入强制滚动锁；
- 不把移动端搜索框改为顶部 fixed；
- 不拆成多个首屏阻塞 CSS 请求；
- 不在本阶段迁移收藏数据。

### 9.6 验收标准

- 视觉符合极简玻璃方向；
- 首屏信息层级清楚；
- 桌面布局不因移动适配而退化；
- 搜索进入与退出无跳动；
- 输入框字号不低于 16px；
- 轻量模式可用；
- 页面在纯色或亮色壁纸上仍可读；
- 首屏加载顺序没有明显退化；
- 自动检查通过。

### 9.7 人工测试

- PC：首页、搜索、收藏入口、设置入口；
- 安卓：输入框、键盘出现、快捷入口换行；
- iPhone Safari：搜索聚焦、背景铺满、安全区；
- 减少动态效果模式；
- 性能轻量模式。

### 9.8 交付物

- 视觉变量与样式分区；
- 新首页骨架；
- Phase 1 前后截图；
- 性能对比；
- 正式版本更新；
- Phase 1 实施记录。

## 10. Phase 2：收藏数据规范化与兼容层

### 10.1 目标

降低新增网站的数据维护成本，消除分类数组和重复默认字段的手工同步。

### 10.2 前置条件

- Phase 1 已稳定；
- 当前 `data/sites.js` 校验无错误；
- 已备份并统计全部分组、分类、隐藏项和特殊字段。

### 10.3 主要涉及文件

- `data/sites.js`
- 可选新增 `data/sites.json`
- `scripts/validate-sites.js`
- 新增 `scripts/migrate-sites.js`
- `js/nav-render.js`
- `api/check.js`
- `scripts/check.js`

### 10.4 实施策略

先建立兼容层，再切换数据源。不得同时删除旧格式和上线新格式。

推荐顺序：

1. 定义新模型和字段映射；
2. 编写迁移脚本；
3. 编写新格式校验；
4. 生成新数据；
5. 对比新旧渲染结果；
6. 更新渲染器兼容两种格式；
7. 切换默认数据源；
8. 稳定后再决定是否删除旧格式。

### 10.5 详细步骤

1. 列出旧字段及用途。
2. 明确以下映射：
   - tab `title` → `group`；
   - item `category` → `category`；
   - `desc` → `description`；
   - `favoriteCheck` → 明确的新布尔语义；
   - `skipCheck` → `statusCheck: false` 或等价语义；
   - `lock` → 分组级隐藏或解锁配置。
3. 为每个站点生成稳定 `id`：
   - 优先使用已有稳定标识；
   - 否则基于名称生成可读 slug；
   - 重复时使用明确后缀；
   - 不直接把完整 URL 当作永久 ID。
4. 从条目自动生成分类列表，首项“全部”由渲染器提供。
5. 把通用 `target` 和 `rel` 移到渲染默认值。
6. 将字符串布尔值迁移为真正布尔值。
7. 图标字段支持：
   - `auto`；
   - 绝对 HTTP(S) 地址；
   - 项目内相对资源。
8. 迁移脚本必须：
   - UTF-8 读写；
   - 默认只预览或输出到新文件；
   - 不静默覆盖现有数据；
   - 检测重复 ID 和 URL；
   - 保留原顺序；
   - 打印迁移统计。
9. 校验脚本必须检查：
   - 必填字段；
   - ID 唯一；
   - URL 协议；
   - 分组合法；
   - 隐藏分组配置；
   - 图标引用；
   - 布尔类型；
   - 重复 URL；
   - 未使用分类。
10. 更新 `/api/check` 的允许域名提取方式，继续只允许收藏数据中的公网 HTTP(S) 域名。
11. 保持本地、内网、环回、metadata 地址拦截。
12. 更新字体字符检查的数据读取方式。

### 10.6 兼容性验证

必须对比：

- 分组数量；
- 每组条目数量；
- 总条目数量；
- 原始顺序；
- 名称；
- URL；
- 分类；
- 描述；
- 图标；
- 状态检测行为；
- 隐藏分组行为。

## 14. Phase 6：JavaScript 职责拆分与渐进式去 jQuery

### 14.1 目标

- 不因为拆文件增加首屏阻塞请求；

   - 点击统计；
   - 数量；
   - 拖动排序；

   - 配置读取；

## 18. 风险登记

### 18.1 iOS 键盘和背景

风险最高。处理原则：

- 优先保持现状；
- 修改前采集真实设备数据；
- 只做局部调整；
- 不变换整个页面；
- 不在键盘动画期间持续写中间视口高度。

### 18.2 数据迁移丢失

必须通过逐条对比、数量统计和隐藏分组检查控制。迁移脚本默认不能直接覆盖。

### 18.3 去 jQuery 回归

以模块为单位迁移。未达到删除条件前继续保留依赖。

### 18.4 玻璃效果性能

限制大面积模糊和动态滤镜，低性能模式提供降级。

### 18.5 本地管理器文件损坏

保存前校验、临时文件写入、写后重新读取。不得把未校验输入直接覆盖正式数据。

### 18.6 首屏请求增加

代码组织和网络加载策略分开考虑。新增模块不等于必须首屏逐文件加载。

## 19. 暂不纳入本轮重构

除非维护者后续明确提出，以下内容不属于本计划：

- 用户账号；
- 云端收藏同步；
- 数据库；
- 在线管理后台；
- PWA 安装与离线缓存；
- 复杂 CMS；
- 多用户权限；
- 严格 CSP 全面改造；
- 外部限流服务；
- React、Vue 或其他大型框架迁移；
- 为多标签而建立复杂标签管理系统；
- 未经真实设备数据支持的 iOS 键盘新方案。

## 20. 完成定义

整个重构只有在以下条件全部满足时才算完成：

8. iPhone Safari 背景、键盘和安全区没有明显回归；
