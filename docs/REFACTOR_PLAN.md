## 2. 已确认的产品决定

以下决定已经由项目维护者确认，后续 Agent 不应反复询问，除非维护者主动改变方向。

### 2.1 “添加标签”的含义

维护者所说的“添加标签麻烦”，主要是指新增一个网站收藏条目麻烦，而不是要求一个网站必须支持复杂的多标签体系。

因此：

- 第一优先级是降低“新增网站”的操作成本；
- 可以保留分类筛选能力；
- 数据结构可以为以后支持多个语义标签留出空间；
- 第一阶段不得为了多标签系统引入复杂交互或复杂数据迁移。

### 2.2 视觉方向

新版继续采用“壁纸 + 极简玻璃感”，不改成厚重的后台面板或传统门户网站。

视觉关键词：

- 克制；
- 通透；
- 留白；
- 清晰层级；
- 低干扰；
- 轻量自然动画；
- 壁纸可见但文字始终可读；
- 桌面端精致，移动端不拥挤。

玻璃效果不得以牺牲首屏速度、文字可读性或低配设备流畅度为代价。`html.perf-lite` 和 `prefers-reduced-motion` 下必须有简化效果。

### 2.3 收藏维护方式

收藏只要求在本地电脑维护。

因此：

- 不建设线上管理后台；
- 不接数据库；
- 不接 GitHub API；
- 不做账号、登录、认证或多端同步；
- 推荐提供本地可视化收藏编辑器；
- 可以附带命令行工具作为批量维护或兜底方式；
- 线上站点不得暴露可写入仓库的管理接口。

## 3. 当前基线与主要问题

本文制定时的只读检查结果如下：

- 项目为纯静态页面，部署目标保持不变；
- `index.html` 约 40 KB，包含较多早期启动及 iOS 高度逻辑；
- `css/style.css` 约 76 KB，桌面、移动端、iOS、动画和组件样式集中维护；
- `js/main.js` 约 32 KB；
- `js/set.js` 约 72 KB；
- `data/sites.js` 约 33 KB；
- 收藏数据为 6 个分组、86 个站点；
- 收藏数据校验为 0 错误、0 警告；
- 主前端脚本中约有 249 处 jQuery 使用；
- 收藏已经做到打开面板后再加载；
- 状态检测已经做到用户需要时再加载；
- 首屏同步样式请求已经收敛为一个主样式；
- 当前工作区在制定计划时无未提交改动。

主要问题不是技术栈过重，而是：

1. 首页、收藏和设置的展示层级不够清楚；
2. 新增网站需要手写较多重复字段；
3. 新增分类需要同步维护分类数组；
4. 大型 CSS 和 JavaScript 文件职责交叉，修改成本逐渐升高；
5. 设置项过于集中，快捷入口与性能设置等概念混放；
6. 现有 jQuery 使用广泛，不能低风险地一次性移除；
7. iOS 兼容逻辑敏感，视觉重构容易误伤已经稳定的行为。

## 4. 总体目标与性能预算

### 4.1 产品目标

重构完成后应达到：

- 首屏突出时间、搜索、常用入口、收藏和设置；
- 收藏面板更容易浏览、搜索和筛选；
- 新增网站通过本地表单完成，不需要手写大段 JavaScript；
- 设置项重新分组，常用设置更容易理解；
- 数据、渲染、交互和样式的职责边界清楚；
- 日常维护命令简洁、可重复；
- 不破坏 PC、安卓和 iPhone Safari 的现有能力。

### 4.2 性能预算

实施过程中应持续守住以下预算：

- 首屏核心结构目标约 0.5 秒可见；
- 时间、搜索框、基础布局和壁纸优先；
- 收藏数据不得阻塞首屏；
- 状态检测不得在未打开收藏时加载；
- 首屏不得批量下载远程收藏图标；
- 首屏真实 stylesheet 链接仍位于早期启动脚本之后；
- 主样式可保持单请求，避免为了代码组织增加阻塞请求；
- 输入响应和高频布局更新继续使用 `requestAnimationFrame` 合帧；
- 动画仅使用适合合成的属性，尽量避免高频改变布局；
- 低性能模式禁用或简化模糊、阴影和复杂动画。

这些是目标预算，不允许 Agent 为追求跑分而破坏视觉稳定、离线容错或 iOS 体验。

## 7. 目标数据模型

第一目标是让新增网站简单，不是建立复杂内容管理系统。

推荐的规范化站点记录：

```json
{
  "id": "github",
  "name": "GitHub",
  "url": "https://github.com/",
  "group": "常用",
  "category": "开发部署",
  "description": "代码托管与协作平台",
  "icon": "auto",
  "featured": true,
  "statusCheck": true
}
```

字段定义：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 是 | 稳定唯一标识；改名或改 URL 时尽量不变 |
| `name` | 是 | 网站显示名称 |
| `url` | 是 | 仅允许绝对 `http` 或 `https` URL |
| `group` | 是 | 一级分组，如常用、影音、工具 |
| `category` | 否 | 组内筛选分类；为空时归入默认分类 |
| `description` | 否 | 简短说明，移动端可按空间省略 |
| `icon` | 否 | `auto`、本地资源或远程资源 |
| `featured` | 否 | 是否允许作为首页快捷入口候选 |
| `statusCheck` | 否 | 是否允许状态检测 |
| `hidden` | 否 | 是否默认不公开展示 |

设计规则：

- `target="_blank"` 与 `rel="noopener noreferrer"` 由渲染器统一提供，不再逐条重复；
- 布尔值必须是真正的布尔类型；
- 分组、分类列表从条目自动推导；
- `id` 必须唯一且稳定；
- URL 必须校验协议；
- 图标为空或为 `auto` 时使用统一的自动与回退策略；
- 旧的 `skipCheck`、`favoriteCheck` 需要在迁移规则中明确映射；
- `奖励` 分组的隐藏和解锁逻辑必须完整保留；
- 不得因为规范化数据而意外公开隐藏内容。

如果后续确有多标签需求，可以新增 `tags: []`，但不属于第一轮必须功能。

## 9. Phase 1：视觉基础与页面骨架

### 9.1 目标

在不改变核心功能的前提下，建立极简玻璃视觉系统和清楚的页面层级，为后续收藏与设置重构提供稳定骨架。

### 9.2 前置条件

- Phase 0 已完成；
- 已有基线截图；
- 已确认主要视口布局；
- iOS 敏感规则位置已经识别。

### 9.3 主要涉及文件

- `index.html`
- `css/style.css`
- 必要时少量修改 `js/main.js`

### 9.4 执行步骤

1. 在 `:root` 建立设计变量：
   - 玻璃背景；
   - 边框颜色；
   - 主文字与次文字；
   - 阴影；
   - 圆角；
   - 间距；
   - 动画时长；
   - 页面最大宽度。
2. 不改变线上单主样式策略，仅重新整理 `style.css` 内部分区。
3. 明确首屏层级：
   - 时间和日期；
   - 搜索；
   - 快捷入口；
   - 收藏与设置入口；
   - 页脚。
4. 统一玻璃面板语言：
   - 背景透明度；
   - 细边框；
   - 轻阴影；
   - 可控模糊；
   - hover 与 active 状态。
5. 保证壁纸较亮时文字仍可读，可使用局部遮罩或文字阴影，但不得叠加过重全屏黑层。
6. 高配设备保留完整模糊和过渡。
7. `html.perf-lite` 下减少：
   - `backdrop-filter`；
   - 大面积阴影；
   - 连续滤镜动画；
   - 非必要淡入。
8. `prefers-reduced-motion` 下关闭位移动画和装饰动画。

## 18. 风险登记

### 18.1 iOS 键盘和背景

风险最高。处理原则：

- 优先保持现状；
- 修改前采集真实设备数据；
- 只做局部调整；
- 不变换整个页面；
- 不在键盘动画期间持续写中间视口高度。

### 18.2 数据迁移丢失

必须通过逐条对比、数量统计和隐藏分组检查控制。迁移脚本默认不能直接覆盖。

### 18.3 去 jQuery 回归

以模块为单位迁移。未达到删除条件前继续保留依赖。

### 18.4 玻璃效果性能

限制大面积模糊和动态滤镜，低性能模式提供降级。

### 18.5 本地管理器文件损坏

保存前校验、临时文件写入、写后重新读取。不得把未校验输入直接覆盖正式数据。

### 18.6 首屏请求增加

代码组织和网络加载策略分开考虑。新增模块不等于必须首屏逐文件加载。

## 19. 暂不纳入本轮重构

- 云端收藏同步；
- 数据库；
- 在线管理后台；
- PWA 安装与离线缓存；
- 复杂 CMS；
- 多用户权限；
- 严格 CSP 全面改造；
- 外部限流服务；
- React、Vue 或其他大型框架迁移；
